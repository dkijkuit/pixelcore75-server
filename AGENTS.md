# AGENTS.md

Spring Boot 3.5 server (Java 21, Gradle 9.3) that drives PixelCore75 LED-matrix panels: renders screens (crypto/CoinGecko, soccer/ESPN, F1, weather, clock, images, animations) to RGB565 frames and publishes them over MQTT (topic = panel serial). Single module, no CI, no formatter/linter.

## Commands

```bash
./gradlew bootRun                                  # run app (from repo root, see gotchas)
./gradlew test                                     # full suite
./gradlew test --tests 'CryptoTickerServerApplicationTests'   # single class
./gradlew build -x test                            # build without tests
```

- Java 21 toolchain is auto-provisioned via the foojay resolver; no local JDK 21 needed.

## Tests require running infra

- `CryptoTickerServerApplicationTests` is a `@SpringBootTest` with no test profile or test resources. It loads the real `application.yml`, so it needs Postgres **and** an MQTT broker on localhost — start them first: `docker compose up -d` (Postgres 17 + NanoMQ on 1883 + mqttx-web on 8090).
- The MQTT broker URL is hardcoded in `MqttConfig.java` (`tcp://localhost:1883`), not configurable via `application.yml`.
- `src/test/.../Color565Utils.java` is a manual debug utility, not a real test suite. Some of its cases read `.ttf` files from the repo root that don't exist in the repo, so those cases fail if invoked. Don't treat that as a regression.

## Architecture / repo facts

- Naming mismatch: repo/product is "pixelcore75", but the Java root package is `nl.ctasoftware.crypto.ticker.server` (historical "crypto-ticker-server" name). Put new code in the existing package tree.
- Layers: `controller/` (REST), `service/` (with `screen/` per-screen renderers, `job/` for the scheduled publish loop, `panel/`, `user/`), `repository/`, `model/` (+ `model/dto`, `model/panel/config`), `security/` (JWT access/refresh + ticket auth for SSE).
- Adding a screen type requires touching: `ScreenType`, a config record (sealed — update `ScreenConfig` permits + `@JsonSubTypes`), a `ScreenService` bean, and the exhaustive switch in `PanelScreenJob.renderScreen`. Jackson is strict, so REST/DB JSON must carry every record component.
- ANIMATION screens: `PanelScreenJob` uploads frames per the binary protocol implemented in the sibling `../pixelcore75-firmware` repo (`src/main.cpp`); the panel loops animations from LittleFS itself. The magic bytes (`ANIM`/`ANIF`/`ANIP`), payload layouts (14-byte start = magic + frameCount u16 + delayMs u16 + uploadId u32 + flags u8 + slot u8; frames = v1/RAW wire: magic 4 + frameIdx u16 2 + 4096-byte RGB565 payload = 4102 B, or v2: magic 4 + frameIdx u16 2 + frameFlags u8 + variable body — see the protocol-v2 bullet below; 9-byte `ANIP` play and `ANIL` ack = magic + slot u8 + echoed uploadId u32, all LE), wire-level frame-count limits (2–200), and ≥10 ms delay clamp must match the firmware exactly — changing one side breaks the other. On top of the wire range, GIF/ANIMATION *screens* are validated to 2–60 frames (`AnimationScreenService.MAX_FRAMES` = 60; the frontend auto-trims GIFs to 60 with a user hint) — that 60-frame cap is a screen-type validation only, while other frame-producing screens keep the protocol's full 2–200 wire range (e.g. radar's whole-revolution loops, up to 200 frames). The `uploadId` is a deterministic content hash (`UploadIdHasher` in `service/job/`): SHA-256 over frameCount u32 LE + frameDelayMs u16 LE + flags u8 (masking out the stage-only bit and the codec bits, i.e. `& ~0x07` — both are transport metadata, so staged/inline and v2/RAW uploads of identical content hash identically, keeping the acked-map and the RAW fallback on a single id) + every frame's raw RGB565 payload bytes in order (the ANIF bodies without their magic/index header), truncated to the first 4 digest bytes LE → u32; 0 is reserved ("no hash") and never emitted. Upload model (stage-ahead): during every screen slot the server immediately uploads the *next* screen's animation (stage-only flag) at full speed — no inter-frame pacing — and the panel stores it in one of 32 slot files (`/a0..31.bin`, LittleFS ~4.9MB via the project partition table; a slot = the screen's ordinal among the rotation's animations mod 32) until the boundary, which only sends `/anim/play`. Slots double as a persistent content cache keyed by uploadId: the firmware persists the per-slot id in LittleFS `/slotidx.bin` (written on upload completion, invalidated on eviction, validated against the slot file on play), and the server keeps an in-memory `(serial, slot) → last acked uploadId` map in `AnimationLoadAckService`, populated on every correlated `ANIL` (in-memory only — a server restart loses it → one redundant upload → safe). When the next cycle's content hash matches that map entry, the `ANIM`/`ANIF` upload is skipped entirely: staging just records a hash-cached staged state (the inline boundary path checks the map the same way) and the boundary sends only the 9-byte `ANIP` — the firmware plays and acks on persisted-id + slot-file match, or stays silent on mismatch (evicted/reflashed panel), in which case the server's existing 2 s play-ack timeout falls back to the full inline re-upload, which re-persists the id. If the next animation's slot is the one currently playing (single-animation rotation, or >32 animations wrapping), staging is skipped and that boundary uploads inline instead (the firmware stops the playing animation when the replacement lands so the slot-file rename succeeds). Staging time is subtracted from the current slot (1 s floor) so boundaries stay on schedule; if staging overruns the slot, the previous screen simply holds until it completes (rotation timing drifts). Inline upload is also the fallback at a boundary with nothing staged (server restart, failed staging, rotation starting on an animation) or after a play-ack timeout (2 s, e.g. panel reflashed with wiped FS — the panel evicts idle slot files for space, which is fine since nothing persists). Stutter-free concurrency is a firmware property: the MQTT callback only copies frames into an 8×4 KB RAM ring; `loop()` drains it to flash one 256 B page per pass while an animation plays (a full frame per pass when idle), and gates `client.loop()` when the ring is nearly full so TCP/MQTT backpressure throttles the server; the animation tick advances by exactly one delay per frame (catch-up) so a flash-erase stall holds one frame instead of permanently slowing playback. A static frame stops playback but keeps the slot files. Retained base-topic image lifecycle: static screens publish it retained (so a panel booting during a static slot shows the current screen), and every confirmed animation play clears it with an empty retained publish — a booting panel then gets no base frame and auto-resumes its slot animation; without the clear, a stale retained frame (e.g. `no_config_found.png` from the pre-config era, never replaced by animation-only rotations) would arrive at boot and stop the auto-resumed animation. `AnimationLoadAckService` holds each animation slot until the `ANIL` ack with the matching uploadId (upload: 5 s + 250 ms/frame, max 60 s; play: 2 s) so the display duration counts from playback start, not publish time.
- **Animation protocol v2 (PAL_RLE compressed frames, plan §5)**: `ANIM` flags bit 0 (`0x01`) = stage-only, bits 1–2 (mask `0x06`) = codec — `0` = RAW (byte-identical v1 wire), `1` = PAL_RLE (`ANIM_CODEC_*` constants in `PanelScreenJob`; chosen per upload via `codecBitsFor`, honoring the per-panel downgrade window). Codec-1 uploads carry v2 `ANIF`s: `"ANIF"` + frameIdx u16 LE + frameFlags u8 + body, where frameFlags 0 = RAW body (4096 B RGB565; 4103 B total) and frameFlags 1 = PAL_RLE body: 16-entry RGB565 palette (32 B, entries u16 LE, first-seen order, unused entries zero) + (run u8, colorIdx u8) pairs covering 2048 px — runs never cross the 64-px row boundaries (each row's runs sum exactly 64; run 1–64; colorIdx 0–15) — so a v2 ANIF is 39 + 2×runCount bytes (103–4102 B in practice). Per frame the server sends the smaller of RAW vs RLE (RLE only when strictly smaller AND ≤ 16 distinct colors in the frame); `AnimationFrameCodec` (`service/job/`) implements encode/decode plus that minimum rule. RAW fallback + downgrade: old/mixed-fleet firmware silently drops length-mismatched v2 ANIFs → no `ANIL` → when `awaitLoaded` times out at the existing upload-ack timeout (5 s + 250 ms/frame, max 60 s; inline boundary path and staging alike) the server re-sends the same content as codec 0 under the same uploadId (the content hash masks the codec bits) and records the panel in `AnimationLoadAckService`'s bounded serial→deadline downgrade map, valid 1 h — inside the window both paths send codec 0 directly (staged path included), after it the server re-probes v2 (a lost ack must not wedge a v2-capable panel on RAW forever, and an old panel should not be re-probed every cycle). Slot file v2 on the panel (what codec-1 uploads produce; cross-repo contract with the firmware repo): magic u16 `A2` + frameCount u16 + delayMs u16 + frameCount × u32 absolute blob offsets + blobs (frameFlags u8 + body each); the firmware seeks the offset and decodes into its existing 4 KB RGB565 RAM buffer per animation tick. The SSE preview is unaffected — it streams BufferedImages, never wire frames.
- **ACMD v1 parametric command engine (plan §6; spec is pinned byte-exact — the firmware repo's AGENTS.md carries the same section and `src/main.cpp` implements it)**: new channel `<base>/cmd`, QoS 0, not retained, **no ack** (fire-and-forget; the frame path stays the fallback for unconverted/photographic screens, and emission is gated by `pixelcore75.command-encoding.enabled` — see the ACMD integration bullet below). Batch frame: `"ACMD"` u32 + version u8 (=1) + cmdCount u16 LE + commands. Canvas is 64×32 RGB565; colors u16 LE; coords u8. Two command forms: **fixed** = opcode + fixed args; **payload** = opcode + payloadLen u16 LE + fixed args + payload, where payloadLen counts *only* the trailing payload (e.g. BLIT's x/y/w/h sit between the length field and the RLE payload). Opcodes: `0x00` NOP · `0x01` CLS color u16 · `0x02` PIX x,y u8 + color u16 · `0x03` LINE x0,y0,x1,y1 u8×4 + color (GFX `drawLine`) · `0x04` RECT x,y,w,h u8×4 + color (outline, GFX `drawRect`) · `0x05` FILL x,y,w,h + color (GFX `fillRect`) · `0x06` CIRC cx,cy u8×2, r u8 + color (GFX `drawCircle`) · `0x07` BLIT (fixed x,y,w,h u8×4; payload = 32 B palette 16×u16 LE + (run u8, colorIdx u8) pairs — the phase-2 PAL_RLE body generalized to w-wide rows: runs never cross rows, each row sums exactly to w, run 1..w, colorIdx 0..15) · `0x10` FONT (payload: pageId u8 0..3 + glyphCount u8 + glyphs [code u8, w u8 1..32, h u8 1..32, xAdvance i8, xOff i8, yOff i8, bitmap h × ceil(w/8) bytes MSB-first]) · `0x11` TEXT (fixed fontId u8, x u8, y u8 = top of glyph line box, color u16; payload: len u8 1..255 + ASCII; glyph at (penX + xOff, y + yOff), penX += xAdvance, unknown glyph → penX += 4) · `0x20` SWEEP cx,cy,r + color u16 + speedDegPerSec u8 1..255 (θ = (elapsedMs × speed / 1000) mod 360; endpoint (cx + r·cosθ, cy + r·sinθ) doubles, C `lround`, GFX line over base; identical-SWEEP commits carry the previous epoch — see the carry-over rule under Execution semantics) · `0x21` SCROLL (fixed x,y,w,h,fontId u8×5 + color u16 + speedMsPerPx u16 LE ≥1; payload len u8 + ASCII; region snapshot at commit, per step restore snapshot then draw text glyph-tops at y with penX = (x + w) − scrolledPx, clipped to the region; restart when penX + textWidth < x, i.e. scrolledPx cycles mod (w + textWidth + 1); textWidth = Σ xAdvance, unknown glyph 4) · `0x22` BLINK x,y,w,h + periodMs u16 (≥2; snapshot; alternate content↔black every periodMs/2). Execution semantics: a batch renders atomically to a base canvas in command order (FONT pages must precede the TEXT/SCROLL that references them; an undefined page renders nothing); the **first** parametric primitive (SWEEP/SCROLL/BLINK) wins, later ones are ignored; **SWEEP phase carry-over**: a commit whose winning SWEEP is identical (cx, cy, r, color, speedDegPerSec) to the live one keeps the previous parametric epoch — elapsed keeps accumulating, so refresh republishes re-arm the sweep exactly where it is and QoS-0 arrival jitter cannot snap the line back to 0° (radar's live refresh relies on this); any parameter change, a different or absent live parametric, or cleared ACMD state (static frame, ANIM/ANIP play, reconnect auto-resume, reboot) arms a fresh epoch (wire format unchanged — old firmware simply keeps the reset behavior); forward compat: any payload-form command is self-delimiting (its extent = fixedArgs + 2 + payloadLen from the v1 opcode table) so a semantic violation inside it only skips that command, while an opcode outside the table has unknowable length and **ends the parsed prefix** (commands before it render). Server implementation in `service/command/`: `CommandBatch` (encoder + TTF font-page extractor via `FontPageExtractor`, same `assets/fonts/*.ttf`), `AcmdParser`, `AcmdMirror` (GFX-exact `GfxCanvas` rasterizer transcribed from the vendored Adafruit_GFX.cpp, `frameAt(elapsedMs)` parametric renderer, `toBufferedImage` preview bridge); BLIT reuses `AnimationFrameCodec`'s palette+RLE core (row-width-generic `encodePalRleBody`/`decodePalRleBody` — one RLE implementation, not a fork).
- **ACMD server integration (plan §6 / phase 3)**: feature flag `pixelcore75.command-encoding.enabled` in `application.yml`, **default false** (mixed-fleet safety: old firmware does not subscribe `<serial>/cmd`), rollout story = flash ACMD-capable firmware first (backward compatible), then enable per deployment; wired via `@Value` in `Px75PanelJobScheduler` → `PanelScreenJob.commandEncodingEnabled` (read once at startup, not runtime-toggled). `CommandScreenService` (`service/screen/`) is the screen-side contract: `byte[] renderCommandBatch(config)` returns a fully framed batch (CLS-black start, self-contained FONT pages, at most one parametric); `renderCommandBatches(config)` (default: the single batch, dwell 0) may instead return a `BatchStream` of page batches the job cycles — first batch at the slot start, each next at `pageDwellMs`, every flip re-guarded by the preview generation (a stale flip thread can never publish after a newer render's batch; the job publishes `/cmd` batches under the serial's generation monitor); `renderCommandRefresh(config)` (default null) may instead return a `RefreshStream(firstBatch, nextBatches supplier, refreshMs)` for live screens: the job publishes the first batch at the slot start, then re-renders via the supplier and republishes on the `refreshMs` grid until the slot ends — pipelined (each next batch renders during the interval before its grid point, so publishes stay exactly one refresh apart however slow the fetch) and grid-skipping (a slow/failed render drops to the next grid point instead of publishing late). The refresh cadence MUST be a whole multiple of the batch parametric's loop period: the panel re-arms the parametric at every commit, so only whole loops restart it exactly where the previous one wrapped (a non-whole cadence visibly snaps the animation back at every refresh; carry-capable firmware makes identical-SWEEP refreshes phase-continuous at any publish time via the epoch carry-over, but the whole-loop rule stays mandatory for SCROLL/BLINK and for mixed fleets on pre-carry firmware). `PanelScreenJob.renderScreen` takes the command path only when the flag is ON **and** the screen's service implements the interface: it clears any retained base image (empty retained publish — command screens publish no retained frame; keep the frame path's clear-on-animation as is), publishes the batch to `<serial>/cmd` QoS 0 not retained, counts the slot from the send time (no ack wait), and drives the SSE preview from `AcmdMirror.frameAt` on the slot's virtual timeline (100 ms tick from send time, generation-superseded — mirrors `streamAnimationPreview`); a `renderCommandBatch` failure logs and falls back to the screen's frame/static path. Flag OFF or non-command service → existing frame/static path byte-for-byte; `stageNextAnimation` skips the frame upload for a next screen that will render via commands. Migrated screens (frame renderers stay intact; the flag chooses at runtime): **CLOCK** = CLS + BLIT of the 11×11 `assets/clock/clock.png` face at (26,5) (14 RGB565 colors — inside BLIT's 16-color palette, byte-exact) + FONT page 0 (EXEPixelPerfect@16f) + centered TEXT of the time (config color; `ClockScreenService.now(ZoneId)` is a protected hook both paths share — freeze it in tests); **NEARBY_AIRCRAFT LIST** = FONT page 1 (cg-pixel@5f) + per-row TEXT: callsign left in altitude color, distance right-aligned white; **CLOSEST** = FONT pages 0+1 + the identity page as TEXT, and — via `CommandScreenService.renderCommandBatches` (the multi-page default-able override returning `BatchStream(batches, pageDwellMs)`) — the registry/route pages as further batches the job republishes at each page dwell (frame-path `closestStream` semantics: identity always, registry/route when enrichment resolves, dwell = slot/pages, one pass, last page holds; page flips are QoS-0 `/cmd` republishes, each fresh batch restarting its parametric — registry/route lines fit-truncate to the canvas instead of scrolling because a batch runs at most one parametric); **RADAR** = CIRC rings (GFX midpoint circles for the frame path's AWT ovals: r 8/14/7 at (16,16)) + PIX center + 2×2 FILL blips at the frame path's polar projection (fully lit, no sweep-phase decay) + info-column TEXT + ONE SWEEP (one whole revolution per refresh interval) — and via `renderCommandRefresh` a **live refresh**: a freshly re-rendered batch (new adsb.lol fetch → new blips + info column) republished for the whole slot, exactly one whole sweep revolution per interval so the re-armed sweep restarts where the old one wrapped (and the identical-SWEEP epoch carry-over on carry-capable firmware absorbs QoS-0 arrival jitter) (the tracked aircraft is always the closest — white 4×4 selection box — while the info column cycles its `RadarInfoPage`s because the 30 px column cannot show everything: TELEMETRY (distance/altitude/speed) always, ROUTE (origin/destination/owner) and REGISTRY (country/manufacturer/type) when adsbdb enrichment resolves them; frame path spreads the pages evenly over the fixed loop via `radarInfoPage` (whole cycle per modulo-replayed loop), command path slices the slot into exactly pageCount EQUAL page windows — a page swap can only land on a refresh publish, so the cadence itself adapts via `radarRefreshMs(slotMillis, pageCount)`: the largest grid ≤ `RADAR_REFRESH_MS` 2000 that tiles the slot with a whole number of refreshes per page (`radarRefreshesPerPage`), falling back to one refresh per page when the u8 sweep-speed cap (`MIN_RADAR_REFRESH_MS` ≈ 1412) makes the tighter grid infeasible; the SWEEP speed is derived per slot (`radarSweepDegPerSec`) to keep one revolution per refresh — e.g. 30 s/3 pages = 2000 ms @ 180°/s, 10 s/3 pages = 1666 ms @ 216°/s; a fixed 4000 ms dwell used to cut a 10 s slot into 4/4/2 s, the 3rd page 50% short) in the refresh supplier via `radarPageForRenderElapsed` — the page is selected for the batch's TARGET grid point (`render elapsed + refreshMs`, because the job renders pipelined one refresh interval before publishing; picking by render time trails the grid and can push a rotation's last page past the slot end) — whole revolutions, never mid-sweep; the page index clamps to the last page (one page cycle per slot, last page holds through the tail)); (~1.1 KB batch ≈ 0.6 KB/s vs ~328 KB per radar frame loop; the adsb.lol stale-while-revalidate cache's `refreshAfterWrite` is 2 s to match). Line layout: TEXT/SCROLL y = frame-path baseline + `FontPageExtractor.FontPage.lineTop()`; a line whose full string exceeds 64 px becomes one SCROLL of the untruncated text (`SCROLL_MS_PER_PX` 60) instead of the frame path's truncation; font page ids are convention only (batches self-contained): 0 = EXEPixelPerfect@16f, 1 = cg-pixel@5f. Golden-image parity tests (docker-free; mocked `AircraftClient`/`AircraftInfoClient`, frozen clock, shared `FrameParity` reduces both engines to panel RGB565): `service/screen/clock/ClockCommandParityTests`, `service/screen/aircraft/AircraftCommandParityTests`, job-branch integration `service/job/PanelScreenJobCommandTests`. Tolerances: CLOCK/LIST/CLOSEST assert ≥95% pixel equality (budget 102/2048 px; measured 0 — the extractor thresholds the exact outlines AWT fills and these pixel fonts have integer advances; the budget only guards JDK font variance); RADAR budget 160 px (7.8%; measured ≤96) covering the intentional ACMD v1 semantics: 6-segment sweep trail vs single SWEEP line, AWT drawOval vs GFX midpoint-circle rings, static fully-lit blips vs sweep-window dimming.
- Screen images/fonts are loaded via relative paths (`assets/fonts/*.ttf`, `assets/images/*.png`) — the app must run with the repo root as working directory (`bootRun` does; running the built jar from elsewhere breaks font/image loading).
- `generated_images/` is a gitignored scratch dir for rendered output; `assets/` is committed runtime data.
- Persistence: Hibernate `ddl-auto: update` manages the schema. The `spring.flyway` block in `application.yml` is inert — Flyway is not on the classpath and there is no `db/migration`.
- Jackson is configured strict (`fail-on-unknown-properties`, `fail-on-missing-creator-properties`, `fail-on-null-creator-properties` all true): DTOs must match the panel/client JSON exactly or deserialization throws.
- Concurrency is custom: virtual-thread executors in `SchedulerConfiguration` (SSE heartbeats, panel screen jobs). Don't assume `spring.threads.virtual.enabled`.
- SSE live preview: tickets (`SseTicketService`) are validated but never consumed — EventSource auto-reconnect replays the original ticket URL, so single-use tickets turn any transient drop into a permanently stuck preview (1 h TTL bounds replay instead). `SseEmitter.send` is not thread-safe: all sends go through `sendGuarded` in `ImageBroadcasterService` (per-emitter lock), and every send failure (not just `IOException`) unregisters the emitter — an uncaught exception silently cancels the periodic heartbeat task.

## Docker

- Image build (see `BUILD.md`): `docker build -t pixelcore75-server .`
- `compose.build.yaml` is an override file with no top-level `services:` key — use it together with the base file: `docker compose -f compose.yaml -f compose.build.yaml up`. It will not parse on its own.

## Config

- DB credentials in `application.yml` match `compose.yaml` (user/db `pixelcore75`); no `.env` needed for local dev.
- `CRYPTO_API_KEY` / `SOCCER_API_KEY` env vars are optional (CoinGecko/ESPN clients work without them).
- JWT secrets have hardcoded dev defaults in `application.yml`.
