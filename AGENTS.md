# AGENTS.md

Spring Boot 3.5 server (Java 21, Gradle 9.3) that drives PixelCore75 LED-matrix panels: renders screens (crypto/CoinGecko, soccer/ESPN, F1, weather, clock, images, animations) to RGB565 frames and publishes them over MQTT (topic = panel serial). Single module, no CI, no formatter/linter.

## Commands

```bash
./gradlew bootRun                                  # run app (from repo root, see gotchas)
./gradlew test                                     # full suite
./gradlew test --tests 'CryptoTickerServerApplicationTests'   # single class
./gradlew build -x test                            # build without tests
```

- Java 21 toolchain is auto-provisioned via the foojay resolver; no local JDK 21 needed.

## Tests

- `./gradlew test` is hermetic (see docs/optimization-plan.md §6): `CryptoTickerServerApplicationTests` boots the full context against a **Testcontainers Postgres** (Flyway migrates it, JobRunr creates its own tables, Hibernate validates) and needs **no MQTT broker** — the HiveMQ transport connects asynchronously and logs instead of failing when no broker is up. `docker compose up -d` is only needed for a live boot smoke test / on-bench runs. (This box quirk: Testcontainers' bundled docker-java defaults to API 1.32 and the local daemon demands ≥1.40 — fixed machine-locally via `~/.docker-java.properties` with `api.version=1.44`.)
- Everything else (protocol, parity, command, JobRunr integration tests) is docker-free: the tests mock `MqttTransport` and run JobRunr on an in-memory storage provider.
- `src/test/.../Color565Utils.java` is a manual debug utility, not a real test suite. Some of its cases read `.ttf` files from the repo root that don't exist in the repo, so those cases fail if invoked. Don't treat that as a regression.

## Architecture / repo facts

- Naming mismatch: repo/product is "pixelcore75", but the Java root package is `nl.ctasoftware.crypto.ticker.server` (historical "crypto-ticker-server" name). Put new code in the existing package tree.
- **Scheduling (docs/optimization-plan.md §4)**: the rotation runs on **JobRunr 8.8.2** (Postgres-backed, dashboard at `http://localhost:8000/dashboard`). `PanelRotationJob.execute(serial, jobId)` renders one slot per execution: it loads panel + config **from the DB every run**, then persists its own successor at `slotMillis + 0-250ms` jitter — a crash between run and successor self-heals via `PanelRotationControl.reconcileStartup` (ApplicationReadyEvent). Per-serial transient state (rotation index, one-ahead staged animation, epoch, admission ticket) lives in `RotationStateService`; there are **no interrupts** — a config save kicks a fresh run and the stale one exits at the next safe point (epoch check before every publish; `allowedJobId` gates the successor commit under the state lock). `PATCH /v1/panel` serial changes restart the rotation on the new serial (`onSerialChanged`). Deviation from the plan: JobRunr 8.8.2 **enforces a >= 5 s poll interval against SQL** (`AbstractStorageProvider.validatePollInterval`, no bypass), so slot boundaries can fire up to 5 s late — the panel holds its last frame, so this is visible drift, not breakage. `service/job/` layout: `PanelRotationJob` (orchestrator), `PanelRotationControl` (config-save/delete/startup facade; depends on `PanelRepository`, NOT `Px75PanelService` — the panel service calls into it for deletes and the arrow must stay one-directional), `RotationStateService`, `RotationPlanner` (hydration/filtering/slot math), `AnimationTransport` (ANIM staging + boundary commit + payload builders), `CommandPublisher` (ACMD branch incl. refresh/page cycles, publishes `/cmd` under the serial's epoch monitor), `PreviewStreamer` (SSE loops + async deduped `generated_images` archive). `PanelJobMdcFilter` puts `serial`/`jobId` on the MDC.
- **MQTT (plan §5)**: all publishes/subscriptions go through the `MqttTransport` seam (`service/mqtt/`); production is `HiveMqMqttTransport` (HiveMQ MQTT 3.1.1 client, `com.hivemq:hivemq-mqtt-client`), tests use mocks — no Paho, no spring-integration-mqtt. Connection settings live in `MqttProperties` (`pixelcore75.mqtt.*`, `@ConfigurationProperties`): `broker-url` (default `tcp://localhost:1883`, env `PIXELCORE75_MQTT_BROKER_URL`) and `client-id` (default `pixelcore75-server`, env `PIXELCORE75_MQTT_CLIENT_ID`) — the client id MUST stay stable across restarts because the transport connects with `cleanSession(false)`; a random per-boot id orphans a persistent broker session. Boot does NOT fail when the broker is down (deliberate change from Paho's fail-fast): the client auto-reconnects and `MqttConfig.awaitBrokerConnection` logs a bounded-timeout warning. The `+/anim/loaded` subscription is re-registered on every connected callback (NanoMQ session persistence is not trusted). `/anim/*` publishes go through `AnimationTransport`'s bounded in-flight window (8 un-acked messages) — that's the backpressure the firmware's RAM ring expects (Paho's per-message blocking was the accidental previous pacing).
- Layers: `controller/` (REST), `service/` (with `screen/` per-screen renderers, `job/` for the scheduled publish loop, `panel/`, `user/`), `repository/`, `model/` (+ `model/dto`, `model/panel/config`), `security/` (JWT access/refresh + ticket auth for SSE).
- Adding a screen type requires touching: `ScreenType`, a config record (sealed — update `ScreenConfig` permits + `@JsonSubTypes`), a `ScreenService` bean, and (if bitmap) `StaticScreenService`/`FrameScreenService` or (command-capable) `CommandScreenService` — `PanelRotationJob.renderScreen` dispatches by interface: command → frame → static. Jackson is strict, so REST/DB JSON must carry every record component.
- CUSTOM screens (user-designed, see `docs/custom-screens-design.md` — normative spec): the whole design lives as a `.pxd` v1 **or v2** JSON **string** inside `CustomScreenConfig.design`, so pxd schema evolution never touches the record contract. A rotation entry carries **exactly one** of `customScreenId` (reference to the user-owned library, `px75_custom_screen`) or `design` (legacy inline) — the compact constructor enforces it and a delegating `@JsonCreator` accepts either JSON shape under the strict mapper; serialization omits the unset one (`@JsonInclude(NON_NULL)`). Library CRUD lives under `/v1/screen/custom` (`CustomScreenController` + `CustomScreenLibraryService`): mine + others' shared (admin all), detail includes `design` + `usageCount` (jsonb containment count on `px75_panel_config.screens_config`); `PxdDesign.java` parses/validates it (lenient on unknown fields, §3.4 rules: 1–60 frames, ≤16-font registry, 64×32 bitmaps, ≤512 KB). 1 frame → static retained frame; 2–60 frames → the normal ANIM pipeline via `FrameScreenConfig`. Library saves dry-compile the design and regenerate the thumbnail (first preview frame); panel-config saves run `CustomScreenLibraryService.validateRotation` (existence + owner/shared/admin visibility + dry-compile) from `PanelController`. `PanelRotationJob` (via `RotationPlanner`) hydrates references **every cycle** via the injected `CustomScreenResolver` (identity resolver in tests), so library edits propagate live; dangling references are skipped with a warning and an all-dangling rotation shows the no-config image while retrying every 30 s. Render does no access checks (a referenced screen keeps rendering after unshare until the config is saved again). Designs are previewed via `POST /v1/screen/custom/preview`; `GET /v1/screen/custom/fontpage/{font}` serves a pxd font's extracted ACMD FONT page (base64 MSB-first glyph bitmaps + `ascent`/`lineTop`, 400 on unknown ids) so the frontend designer's edit canvas composites text pixel-exact with the panel's own TEXT rules instead of approximating with browser fonts. **pxd v2 = v1 + parametric layers (§3.6: `sweep`/`scroll`/`blink`, mapping 1:1 onto the ACMD parametrics)**: a design carrying any parametric layer must be command-compilable (§3.4.7 — single frame, ≤4 parametrics, ≤4 distinct text/scroll fonts, bitmap ≤16 RGB565 colors, coords 0..255) and `CustomScreenService implements CommandScreenService` for exactly those designs (`commandCapable` = has-parametrics; the job gates the command branch AND the ANIM staging skip on it — frame designs keep the retained/ANIM pipelines). Command compile: CLS + hoisted FONT pages + one command per layer in order (`bitmap`→BLIT via alpha-composited RGB565, `text`→TEXT with y = baseline+lineTop, `circle` r=0→PIX); the frame path bakes the t=0 pose (θ=0 sweep line, clipped head-hold scroll text, no-op blink) for thumbnails, the preview endpoint and the library's retained pipeline; the preview endpoint samples `AcmdMirror.frameAt` at 100 ms for `clamp(maxParametricLoopMs, 2000, 10000)` — same response shape (parity pinned by `CustomScreenCommandTests`, measured 0 px). Keep the spec, the frontend TS mirror (`src/types/pxd.ts` in the sibling repo), and `PxdDesign.java` in sync — the pxd format is a cross-repo contract like the ANIM protocol.
- ANIMATION screens: `AnimationTransport` (`service/job/`) uploads frames per the binary protocol implemented in the sibling `../pixelcore75-firmware` repo (`src/main.cpp`); the panel loops animations from LittleFS itself. The magic bytes (`ANIM`/`ANIF`/`ANIP`), payload layouts (14-byte start = magic + frameCount u16 + delayMs u16 + uploadId u32 + flags u8 + slot u8; frames = v1/RAW wire: magic 4 + frameIdx u16 2 + 4096-byte RGB565 payload = 4102 B, or v2: magic 4 + frameIdx u16 2 + frameFlags u8 + variable body — see the protocol-v2 bullet below; 9-byte `ANIP` play and `ANIL` ack = magic + slot u8 + echoed uploadId u32, all LE), wire-level frame-count limits (2–200), and ≥10 ms delay clamp must match the firmware exactly — changing one side breaks the other. On top of the wire range, GIF/ANIMATION *screens* are validated to 2–60 frames (`AnimationScreenService.MAX_FRAMES` = 60; the frontend auto-trims GIFs to 60 with a user hint) — that 60-frame cap is a screen-type validation only, while other frame-producing screens keep the protocol's full 2–200 wire range (e.g. radar's whole-revolution loops, up to 200 frames). The `uploadId` is a deterministic content hash (`UploadIdHasher` in `service/job/`): SHA-256 over frameCount u32 LE + frameDelayMs u16 LE + flags u8 (masking out the stage-only bit and the codec bits, i.e. `& ~0x07` — both are transport metadata, so staged/inline and v2/RAW uploads of identical content hash identically, keeping the acked-map and the RAW fallback on a single id) + every frame's raw RGB565 payload bytes in order (the ANIF bodies without their magic/index header), truncated to the first 4 digest bytes LE → u32; 0 is reserved ("no hash") and never emitted. Upload model (stage-ahead): during every screen slot the server immediately uploads the *next* screen's animation (stage-only flag) at full speed — no inter-frame pacing — and the panel stores it in one of 32 slot files (`/a0..31.bin`, LittleFS ~4.9MB via the project partition table; a slot = the screen's ordinal among the rotation's animations mod 32) until the boundary, which only sends `/anim/play`. Slots double as a persistent content cache keyed by uploadId: the firmware persists the per-slot id in LittleFS `/slotidx.bin` (written on upload completion, invalidated on eviction, validated against the slot file on play), and the server keeps an in-memory `(serial, slot) → last acked uploadId` map in `AnimationLoadAckService`, populated on every correlated `ANIL` (in-memory only — a server restart loses it → one redundant upload → safe). When the next cycle's content hash matches that map entry, the `ANIM`/`ANIF` upload is skipped entirely: staging just records a hash-cached staged state (the inline boundary path checks the map the same way) and the boundary sends only the 9-byte `ANIP` — the firmware plays and acks on persisted-id + slot-file match, or stays silent on mismatch (evicted/reflashed panel), in which case the server's existing 2 s play-ack timeout falls back to the full inline re-upload, which re-persists the id. If the next animation's slot is the one currently playing (single-animation rotation, or >32 animations wrapping), staging is skipped and that boundary uploads inline instead (the firmware stops the playing animation when the replacement lands so the slot-file rename succeeds). Staging time is subtracted from the current slot (1 s floor) so boundaries stay on schedule; if staging overruns the slot, the previous screen simply holds until it completes (rotation timing drifts). Inline upload is also the fallback at a boundary with nothing staged (server restart, failed staging, rotation starting on an animation) or after a play-ack timeout (2 s, e.g. panel reflashed with wiped FS — the panel evicts idle slot files for space, which is fine since nothing persists). Stutter-free concurrency is a firmware property: the MQTT callback only copies frames into an 8×4 KB RAM ring; `loop()` drains it to flash one 256 B page per pass while an animation plays (a full frame per pass when idle), and gates `client.loop()` when the ring is nearly full so TCP/MQTT backpressure throttles the server; the animation tick advances by exactly one delay per frame (catch-up) so a flash-erase stall holds one frame instead of permanently slowing playback. A static frame stops playback but keeps the slot files. Retained base-topic image lifecycle: static screens publish it retained (so a panel booting during a static slot shows the current screen), and every confirmed animation play clears it with an empty retained publish — a booting panel then gets no base frame and auto-resumes its slot animation; without the clear, a stale retained frame (e.g. `no_config_found.png` from the pre-config era, never replaced by animation-only rotations) would arrive at boot and stop the auto-resumed animation. `AnimationLoadAckService` holds each animation slot until the `ANIL` ack with the matching uploadId (upload: 5 s + 250 ms/frame, max 60 s; play: 2 s) so the display duration counts from playback start, not publish time.
- **Animation protocol v2 (PAL_RLE compressed frames, plan §5)**: `ANIM` flags bit 0 (`0x01`) = stage-only, bits 1–2 (mask `0x06`) = codec — `0` = RAW (byte-identical v1 wire), `1` = PAL_RLE (`ANIM_CODEC_*` constants in `AnimationTransport`; chosen per upload via `codecBitsFor`, honoring the per-panel downgrade window). Codec-1 uploads carry v2 `ANIF`s: `"ANIF"` + frameIdx u16 LE + frameFlags u8 + body, where frameFlags 0 = RAW body (4096 B RGB565; 4103 B total) and frameFlags 1 = PAL_RLE body: 16-entry RGB565 palette (32 B, entries u16 LE, first-seen order, unused entries zero) + (run u8, colorIdx u8) pairs covering 2048 px — runs never cross the 64-px row boundaries (each row's runs sum exactly 64; run 1–64; colorIdx 0–15) — so a v2 ANIF is 39 + 2×runCount bytes (103–4102 B in practice). Per frame the server sends the smaller of RAW vs RLE (RLE only when strictly smaller AND ≤ 16 distinct colors in the frame); `AnimationFrameCodec` (`service/job/`) implements encode/decode plus that minimum rule. RAW fallback + downgrade: old/mixed-fleet firmware silently drops length-mismatched v2 ANIFs → no `ANIL` → when `awaitLoaded` times out at the existing upload-ack timeout (5 s + 250 ms/frame, max 60 s; inline boundary path and staging alike) the server re-sends the same content as codec 0 under the same uploadId (the content hash masks the codec bits) and records the panel in `AnimationLoadAckService`'s bounded serial→deadline downgrade map, valid 1 h — inside the window both paths send codec 0 directly (staged path included), after it the server re-probes v2 (a lost ack must not wedge a v2-capable panel on RAW forever, and an old panel should not be re-probed every cycle). Slot file v2 on the panel (what codec-1 uploads produce; cross-repo contract with the firmware repo): magic u16 `A2` + frameCount u16 + delayMs u16 + frameCount × u32 absolute blob offsets + blobs (frameFlags u8 + body each); the firmware seeks the offset and decodes into its existing 4 KB RGB565 RAM buffer per animation tick. The SSE preview is unaffected — it streams BufferedImages, never wire frames.
- **ACMD v1 parametric command engine (plan §6; spec is pinned byte-exact — the firmware repo's AGENTS.md carries the same section and `src/main.cpp` implements it)**: new channel `<base>/cmd`, QoS 0, not retained, **no ack** (fire-and-forget; every command-capable screen renders via commands only — bitmap screens (ANIMATION, IMAGE, non-parametric CUSTOM designs) keep the static/ANIM paths — see the ACMD integration bullet below). Batch frame: `"ACMD"` u32 + version u8 (=1) + cmdCount u16 LE + commands. Canvas is 64×32 RGB565; colors u16 LE; coords u8. Two command forms: **fixed** = opcode + fixed args; **payload** = opcode + payloadLen u16 LE + fixed args + payload, where payloadLen counts *only* the trailing payload (e.g. BLIT's x/y/w/h sit between the length field and the RLE payload). Opcodes: `0x00` NOP · `0x01` CLS color u16 · `0x02` PIX x,y u8 + color u16 · `0x03` LINE x0,y0,x1,y1 u8×4 + color (GFX `drawLine`) · `0x04` RECT x,y,w,h u8×4 + color (outline, GFX `drawRect`) · `0x05` FILL x,y,w,h + color (GFX `fillRect`) · `0x06` CIRC cx,cy u8×2, r u8 + color (GFX `drawCircle`) · `0x07` BLIT (fixed x,y,w,h u8×4; payload = 32 B palette 16×u16 LE + (run u8, colorIdx u8) pairs — the phase-2 PAL_RLE body generalized to w-wide rows: runs never cross rows, each row sums exactly to w, run 1..w, colorIdx 0..15) · `0x10` FONT (payload: pageId u8 0..3 + glyphCount u8 + glyphs [code u8, w u8 1..32, h u8 1..32, xAdvance i8, xOff i8, yOff i8, bitmap h × ceil(w/8) bytes MSB-first]) · `0x11` TEXT (fixed fontId u8, x u8, y u8 = top of glyph line box, color u16; payload: len u8 1..255 + ASCII; glyph at (penX + xOff, y + yOff), penX += xAdvance, unknown glyph → penX += 4) · `0x20` SWEEP cx,cy,r + color u16 + speedDegPerSec u8 1..255 (θ = (elapsedMs × speed / 1000) mod 360; endpoint (cx + r·cosθ, cy + r·sinθ) doubles, C `lround`, GFX line over base; an identical parametric sequence carries the previous epoch — see the carry-over rule under Execution semantics) · `0x21` SCROLL (fixed x,y,w,h,fontId u8×5 + color u16 + speedMsPerPx u16 LE ≥1; payload len u8 + ASCII; ping-pong marquee with pacing — the per-tick full-base copy restores the region, then the text draws glyph-tops at y with penX oscillating between the head-visible extreme x and the tail-visible extreme x + w − textWidth, clipped to the region; each extreme is held for `SCROLL_HOLD_PX` 8 px-units before reversing and one pass travels textWidth − w px in at least `SCROLL_MIN_PASS_PX` 12 px-units (one px-unit = speedMsPerPx — a barely-overflowing text glides instead of rattling); phase 0 = the head hold; a fitting text renders statically at x; textWidth = Σ xAdvance, unknown glyph 4) · `0x22` BLINK x,y,w,h + periodMs u16 (≥2; alternate content (the base region) ↔ black every periodMs/2). Execution semantics: a batch renders atomically to a base canvas in command order (FONT pages must precede the TEXT/SCROLL that references them; an undefined page renders nothing); a batch arms **all** its parametric primitives (SWEEP/SCROLL/BLINK), in command order, up to **4** (`ACMD_PARAMS_MAX`/`AcmdOpcode.PARAMS_MAX`; further ones are validated but ignored) — each parametric tick (~10 ms floor) starts from a fresh copy of the immutable committed base (that copy IS the SCROLL/BLINK region-snapshot restore) and applies the overlays in command order, so a later overlay draws over an earlier one where their regions overlap; **epoch carry-over**: a commit whose armed parametric SEQUENCE is identical to the live one (same count, order, types, parameters — SCROLL text included) keeps the previous epoch, so every overlay's phase runs continuously across refresh republishes (radar's live refresh AND its bouncing info-column lines rely on this — an identical republish cannot snap the sweep to 0° or restart a marquee mid-bounce); any change (different sequence, fewer/more parametrics, none) or cleared ACMD state (static frame, ANIM/ANIP play, reconnect auto-resume, reboot) arms all parametrics fresh; forward compat: any payload-form command is self-delimiting (its extent = fixedArgs + 2 + payloadLen from the v1 opcode table) so a semantic violation inside it only skips that command, while an opcode outside the table has unknowable length and **ends the parsed prefix** (commands before it render). Server implementation in `service/command/`: `CommandBatch` (encoder + TTF font-page extractor via `FontPageExtractor`, same `assets/fonts/*.ttf`), `AcmdParser`, `AcmdMirror` (GFX-exact `GfxCanvas` rasterizer transcribed from the vendored Adafruit_GFX.cpp, `frameAt(elapsedMs)` parametric renderer, `toBufferedImage` preview bridge); BLIT reuses `AnimationFrameCodec`'s palette+RLE core (row-width-generic `encodePalRleBody`/`decodePalRleBody` — one RLE implementation, not a fork).
- **ACMD server integration (plan §6 / phase 3)**: the command path is **unconditional** — the old `pixelcore75.command-encoding.enabled` rollout flag is removed (its mixed-fleet safety period is over: the fleet runs ACMD firmware, and the frame/ANIM fallback proved inferior — a slow bitmap upload stacks ack timeouts inside the slot and stalls the rotation). Every `CommandScreenService` screen renders via commands only; a failed batch build logs and the slot holds the previous screen (no fallback encoding). Bitmap screens (ANIMATION, IMAGE, non-parametric CUSTOM designs) keep the static/ANIM pipeline via `StaticScreenService`/`FrameScreenService`. `CommandScreenService` (`service/screen/`) is the screen-side contract: `byte[] renderCommandBatch(config)` returns a fully framed batch (CLS-black start, self-contained FONT pages, up to `AcmdOpcode.PARAMS_MAX` parametrics); `commandCapable(config)` (default true) lets a service opt specific configs out of the command branch (CUSTOM: only pxd v2 parametric designs) — the job gates both the command path and the ANIM staging skip on it, so an incapable config never builds a failing batch and never loses its staging; `renderCommandBatches(config)` (default: the single batch, dwell 0) may instead return a `BatchStream` of page batches the job cycles — first batch at the slot start, each next at `pageDwellMs`, every flip re-guarded by the preview generation (a stale flip thread can never publish after a newer render's batch; the job publishes `/cmd` batches under the serial's generation monitor); `renderCommandRefresh(config)` (default null) may instead return a `RefreshStream(firstBatch, nextBatches supplier, refreshMs)` for live screens: the job publishes the first batch at the slot start, then re-renders via the supplier and republishes on the `refreshMs` grid until the slot ends — pipelined (each next batch renders during the interval before its grid point, so publishes stay exactly one refresh apart however slow the fetch) and grid-skipping (a slow/failed render drops to the next grid point instead of publishing late). The refresh cadence MUST be a whole multiple of every parametric's loop period whenever the parametric sequence CHANGES between refreshes (page swaps, changing data): changed sequences re-arm all parametrics at 0, so only whole loops restart exactly where the previous one wrapped — identical sequences instead carry the epoch (phase-continuous at any publish time, the radar's stable bouncing lines rely on this), but the whole-loop rule stays the safe default for anything that re-arms. `PanelRotationJob.renderScreen` takes the command path whenever the screen's service implements the interface: it clears any retained base image (empty retained publish — command screens publish no retained frame; keep the frame path's clear-on-animation as is), publishes the batch to `<serial>/cmd` QoS 0 not retained, counts the slot from the send time (no ack wait), and drives the SSE preview from `AcmdMirror.frameAt` on the slot's virtual timeline (100 ms tick from send time, generation-superseded — mirrors `streamAnimationPreview`); a `renderCommandBatch` failure logs and the panel holds its previous screen (no inferior fallback). Non-command services keep the existing frame/static path byte-for-byte; `stageNextAnimation` skips the frame upload for a next screen that will render via commands. Command screens (the old frame/static renderers are deleted; golden-snapshot tests): **CLOCK** = CLS + BLIT of the 11×11 `assets/clock/clock.png` face at (26,5) (14 RGB565 colors — inside BLIT's 16-color palette, byte-exact) + FONT page 0 (EXEPixelPerfect@16f) + centered TEXT of the time (config color; `ClockScreenService.now(ZoneId)` is a protected hook both paths share — freeze it in tests); **NEARBY_AIRCRAFT LIST** = FONT page 1 (cg-pixel@5f) + per-row TEXT: callsign left in altitude color, distance right-aligned white; **CLOSEST** = FONT pages 0+1 + the identity page as TEXT, and — via `CommandScreenService.renderCommandBatches` (the multi-page default-able override returning `BatchStream(batches, pageDwellMs)`) — the registry/route pages as further batches the job republishes at each page dwell (frame-path `closestStream` semantics: identity always, registry/route when enrichment resolves, dwell = slot/pages, one pass, last page holds; page flips are QoS-0 `/cmd` republishes, each fresh batch restarting its parametrics — registry/route lines fit-truncate to the canvas (fitting by pixels, not the frame path's char counts)); **RADAR** = CIRC rings (GFX midpoint circles for the frame path's AWT ovals: r 8/14/7 at (16,16)) + PIX center + 2×2 FILL blips at the frame path's polar projection (fully lit, no sweep-phase decay), with the tracked blip rendered as a plain WHITE 3×3 fill (`TRACKED_BLIP_SIZE` — unique through size + color alone, every other blip 2×2 altitude-colored; no selection box, ring, or motion tail; drawn last, undimmed — a selection marker, not data) + info-column lines (TEXT when a line fits the 30 px column — `INFO_COLUMN_WIDTH`; overflowing lines become SCROLLs of the full untruncated text ping-ponging across the column — right-to-left until the tail is visible, then back — up to `RADAR_COLUMN_MAX_SCROLLS` = PARAMS_MAX − 1 marquees ticking alongside the SWEEP — stable lines like owner/country bounce continuously across refreshes via the epoch carry-over, while the frame path keeps its char truncation, the CLOSEST precedent; further overflowing lines pixel-fit-truncate) + ONE SWEEP (one whole revolution per refresh interval) — and via `renderCommandRefresh` a **live refresh**: a freshly re-rendered batch (new adsb.lol fetch → new blips + info column) republished for the whole slot, exactly one whole sweep revolution per interval so the re-armed sweep restarts where the old one wrapped (and the identical-sequence epoch carry-over on carry-capable firmware absorbs QoS-0 arrival jitter, scrolls included) (the tracked aircraft is always the closest — white 3×3 blip — while the info column cycles its `RadarInfoPage`s because the 30 px column cannot show everything: TELEMETRY (distance/altitude/speed) always, ROUTE (origin/destination/owner) and REGISTRY (country/manufacturer/type) when adsbdb enrichment resolves them; frame path spreads the pages evenly over the fixed loop via `radarInfoPage` (whole cycle per modulo-replayed loop), command path slices the slot into exactly pageCount EQUAL page windows — a page swap can only land on a refresh publish, so the cadence itself adapts via `radarRefreshMs(slotMillis, pageCount)`: the largest grid ≤ `RADAR_REFRESH_MS` 2000 that tiles the slot with a whole number of refreshes per page (`radarRefreshesPerPage`), falling back to one refresh per page when the u8 sweep-speed cap (`MIN_RADAR_REFRESH_MS` ≈ 1412) makes the tighter grid infeasible; the SWEEP speed is derived per slot (`radarSweepDegPerSec`) to keep one revolution per refresh — e.g. 30 s/3 pages = 2000 ms @ 180°/s, 10 s/3 pages = 1666 ms @ 216°/s; a fixed 4000 ms dwell used to cut a 10 s slot into 4/4/2 s, the 3rd page 50% short) in the refresh supplier via `radarPageForRenderElapsed` — the page is selected for the batch's TARGET grid point (`render elapsed + refreshMs`, because the job renders pipelined one refresh interval before publishing; picking by render time trails the grid and can push a rotation's last page past the slot end) — whole revolutions, never mid-sweep; the page index clamps to the last page (one page cycle per slot, last page holds through the tail)); (~1.1 KB batch ≈ 0.6 KB/s vs ~328 KB per radar frame loop; the adsb.lol stale-while-revalidate cache's `refreshAfterWrite` is 2 s to match). Data freshness split inside `AircraftScreenService`: slot-start renders (CLOSEST/LIST, the RADAR first batch and frame-path loop) read via `AircraftClient.getAircraftFresh` — a foreground loader run (retry envelope) whose result is displayed and `put` back into the cache, degrading to the last good snapshot on total provider failure — because the SWR read serves the PREVIOUS fetch's snapshot to the first reader after a quiet period (a once-per-slot screen whose key nothing else polls showed one-rotation-old data next to radar's 2 s polling: the "closest screen older than radar" bug); any read of a refresh-stale entry (`get`/`getIfPresent`/`asMap.get` alike) schedules the background reload, so the fresh path touches the cache only after its own load to avoid double-fetching; only the radar refresh supplier keeps the instant SWR read (`getCachedAircraft`), pinned by `AdsbLolAircraftClientFreshnessTests`. Line layout: TEXT/SCROLL y = frame-path baseline + `FontPageExtractor.FontPage.lineTop()`; a line whose full string exceeds 64 px becomes one SCROLL of the untruncated text (`SCROLL_MS_PER_PX` 120) instead of the frame path's truncation; font page ids are convention only (batches self-contained): 0 = EXEPixelPerfect@16f, 1 = cg-pixel@5f. Shared helpers for the text-only migrations: `service/command/AcmdLayout` (sanitize via `LatinFoldService.foldToAsciiStrict` — the same fold the frame path's `drawText*` applies, with a strict-ASCII tail so `requireAscii` can never fail a batch on one enriched field — plus left/right/center TEXT emission at the frame path's baselines) and `Rgb565.pixels(BufferedImage)` (ARGB→RGB565 with transparent→black, the frame path's black-canvas composite, for asset BLITs). Further command screens (static single batches): **DATE** = CLS + BLIT of the 11×11 `assets/calendar/calendar11px.png` glyph at (26,5) (7 RGB565 colors) + centered date TEXT in a grinched-4x7@9f page (config color; a `now(ZoneId)` protected hook like the clock's freezes both paths in tests); **WEATHER_FORECAST** = per-cell WMO icon BLITs at x=i·16 (committed pixel assets, ≤6 colors each) + day/max/min TEXT rows in a TinyUnicode@16f page; **SOCCER_MATCH** = FONT pages 0+1 with home abbreviation left / away right in RGB565-quantized shirt colors (the `getShirtColor` lift shared with the frame path), score and status line (live `matchTime` / "Full time" / kickoff date) centered, plus the no-match page; **FORMULA1** = cg-pixel TEXT for all four detail types (standings rows with right-aligned points and per-team colors, calendar rows with 5×5 country-flag BLITs, centered next-event lines, F1-logo 19×7 BLIT + next-session lines — all committed assets inside the 16-color palette; flag/logo/icon BLITs read the same files the frame path reads per render, so a >16-color asset fails the batch build and falls back, never diverges); **CRYPTO_TICKER** = led-board TEXT (symbol, right-aligned 24h %, currency+price) + the sparkline as one vertical LINE + blue PIX per history point (`drawSparkLine`'s exact geometry; the ASCII `$` rides in the price TEXT, while the non-ASCII €/£ — both glyphs exist in EXEPixelPerfect.ttf — BLIT as AWT-rasterized glyphs (`drawString` with AA off + the extractor's α≥128 threshold, transparent→black) with the price TEXT starting at the symbol's AWT advance, the frame path's own pen position; a raster-empty glyph degrades to the sanitized TEXT, never a failed batch). Golden-snapshot tests (docker-free; mocked `AircraftClient`/`AircraftInfoClient`, frozen clock, shared `CommandGolden` pins the ACMD mirror's panel RGB565 via recorded SHA-256 digests — regenerate with `-Dpixelcore75.golden.record=true` / env `PIXELCORE75_GOLDEN_RECORD=1` and review the diff; digests in `service/command/GoldenDigest`): `service/screen/clock/ClockCommandParityTests`, `service/screen/aircraft/AircraftCommandParityTests`, `service/screen/date/DateCommandParityTests`, `service/screen/weather/WeatherCommandParityTests`, `service/screen/soccer/SoccerCommandParityTests`, `service/screen/formula1/Formula1CommandParityTests`, `service/screen/crypto/CryptoCommandParityTests` (mocked clients, deterministic data), job-branch integration `service/job/PanelRotationJobCommandTests`. The digests are byte-exact and deterministic (the old cross-engine parity budgets were 102/2048 px for text screens and 160 px for RADAR, measured 0/≤96 — the extractor thresholds the exact outlines AWT fills and these pixel fonts have integer advances; the budgets only ever guarded JDK font variance, and ACMD v1's intentional semantics vs the old frame engine were the 6-segment sweep trail vs single SWEEP line, AWT drawOval vs GFX midpoint-circle rings, and statically fully-lit blips vs sweep-window dimming); **CUSTOM** parametric designs (pxd v2 §3.6, see the custom-screens bullet) compile via the same `commandCapable` gate — only designs with sweep/scroll/blink layers take the command branch, everything else keeps the retained-frame/ANIM paths (`CustomScreenCommandTests` pins the t=0 baked-vs-mirror parity, measured 0 px).
- Screen images/fonts are loaded via relative paths (`assets/fonts/*.ttf`, `assets/images/*.png`) — the app must run with the repo root as working directory (`bootRun` does; running the built jar from elsewhere breaks font/image loading).
- `generated_images/` is a gitignored scratch dir for rendered output; `assets/` is committed runtime data.
- Persistence: **Flyway manages the schema** (`db/migration`, plan §3); `V1__baseline.sql` is a `pg_dump` of the live schema at adoption, existing DBs baseline at version 1 (`baseline-on-migrate`, `baseline-version: 1`), and Hibernate runs with `ddl-auto: validate` — write forward-only migrations, never edit V1. JobRunr creates/owns its own `jobrunr_*` tables outside Flyway.
- Jackson is configured strict (`fail-on-unknown-properties`, `fail-on-missing-creator-properties`, `fail-on-null-creator-properties` all true): DTOs must match the panel/client JSON exactly or deserialization throws.
- Concurrency is custom: virtual-thread executors in `SchedulerConfiguration` (SSE heartbeats, panel screen jobs). Don't assume `spring.threads.virtual.enabled`.
- SSE live preview: tickets (`SseTicketService`) are validated but never consumed — EventSource auto-reconnect replays the original ticket URL, so single-use tickets turn any transient drop into a permanently stuck preview (1 h TTL bounds replay instead). `SseEmitter.send` is not thread-safe: all sends go through `sendGuarded` in `ImageBroadcasterService` (per-emitter lock), and every send failure (not just `IOException`) unregisters the emitter — an uncaught exception silently cancels the periodic heartbeat task.

## Docker

- Image build (see `BUILD.md`): `docker build -t pixelcore75-server .`
- `compose.build.yaml` is an override file with no top-level `services:` key — use it together with the base file: `docker compose -f compose.yaml -f compose.build.yaml up`. It will not parse on its own.

## Config

- DB credentials in `application.yml` match `compose.yaml` (user/db `pixelcore75`); no `.env` needed for local dev.
- `CRYPTO_API_KEY` / `SOCCER_API_KEY` env vars are optional (CoinGecko/ESPN clients work without them).
- JWT secrets come from `JWT_SECRET` / `JWT_REFRESH_SECRET` (application.yml defaults are blank). Blank secrets fall back to the hardcoded dev defaults in `JwtService` — EXCEPT under the `prod` profile, where a blank secret fails the boot (fail-fast against known-secret deploys).
